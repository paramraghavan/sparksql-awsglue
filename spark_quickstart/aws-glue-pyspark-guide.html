Set up the lab

Spark, Jupyter and LocalStack all run on the Mac Ultra. Your own computer only shows the notebook in a browser. Spark reaches LocalStack at localhost, which means the Mac, so nothing else needs to be exposed.

Installation is already written up, so these steps point to the guides in spark_quickstart/ in the sparksql-awsglue repo. Step numbers refer to setup-mac-local-spark.md.

  1. Check the Python environment

    The lab lives in ~/spark-glue-local-lab. If it's missing, follow Steps 1 to 6.

def deploy_lambda(name, code, env=None):
    """Zip a handler's source as app.py and (re)deploy it to LocalStack. Returns its ARN."""
    buf = io.BytesIO()
    with zipfile.ZipFile(buf, "w") as z:
        z.writestr("app.py", code)
    try:
        lam.delete_function(FunctionName=name)
    except lam.exceptions.ResourceNotFoundException:
        pass
    lam.create_function(FunctionName=name, Runtime="python3.12", Handler="app.handler", Timeout=30,
                        Role="arn:aws:iam::000000000000:role/lambda-role",   # placeholder; real AWS needs a real role
                        Code={"ZipFile": buf.getvalue()}, Environment={"Variables": env or {}})
    lam.get_waiter("function_active_v2").wait(FunctionName=name)
    return lam.get_function(FunctionName=name)["Configuration"]["FunctionArn"]

def wait_for_keys(prefix, count, seconds=30):
    """S3 triggers run asynchronously, so wait until the expected objects appear."""
    end = time.time() + seconds
    while len(s3_keys(prefix)) < count and time.time() < end:
        time.sleep(0.5)
    return s3_keys(prefix)

def s3_ls(prefix=""):
    """Print the keys under a prefix, hiding Spark's marker objects."""
    paginator = s3.get_paginator("list_objects_v2")
    keys = [o["Key"] for p in paginator.paginate(Bucket=BUCKET, Prefix=prefix) for o in p.get("Contents", [])]
    keys = [k for k in keys if not k.endswith("$folder$")]
    for k in keys:
        print(k[:60] + "..." if len(k) > 63 else k)
    print(f"({len(keys)} objects)")

def s3_keys(prefix=""):
    """Return the keys under a prefix as a list."""
    paginator = s3.get_paginator("list_objects_v2")
    return [o["Key"] for p in paginator.paginate(Bucket=BUCKET, Prefix=prefix) for o in p.get("Contents", [])]

def s3_rm(prefix):
    """Delete every object under a prefix in the lab bucket."""
    keys = s3_keys(prefix)
    for i in range(0, len(keys), 1000):
        s3.delete_objects(Bucket=BUCKET, Delete={"Objects": [{"Key": k} for k in keys[i:i + 1000]]})

def s3_put(key, text):
    """Write a small text object to the lab bucket."""
    s3.put_object(Bucket=BUCKET, Key=key, Body=text.encode())

def reset_db(name):
    """Drop a Spark catalog database and everything in it, then create it again."""
    spark.sql(f"DROP DATABASE IF EXISTS {name} CASCADE")
    spark.sql(f"CREATE DATABASE {name}")

Keeping the lab clean

  • Each question cleans up after itself on rerun. Answers drop and recreate their own tables and prefixes, so you can run them in any order.
  • Use new names in your own answers, and don't reassign orders or curated, because later questions use them.
  • To get back to a clean state, run the setup cell again. It drops this session's tables, empties glue-lab, and reloads the data.
  • After a kernel restart, the Spark catalog is empty, but files stay in LocalStack until the setup cell empties them. Iceberg tables also stay in the bucket until then, since their catalog is stored there.
  • LocalStack reports persistence as disabled, so stopping it should be expected to lose all its buckets, including de-lab. Download anything you need first.

S3: object storage

S3 stores objects in buckets, each named by a key. It isn't a file system: there are no real folders, no rename, and no way to change part of an object. To change a row in a file, you rewrite the file. Almost everything else on this page follows from that.

Example: put, list and read an object
s3_put("demo/2026/01/sales.csv", "id,amount\n1,10\n2,20\n")
s3_put("demo/2026/02/sales.csv", "id,amount\n3,30\n")

print("everything under demo/ :", s3_keys("demo/"))
print("only January           :", s3_keys("demo/2026/01/"))
print(s3.get_object(Bucket=BUCKET, Key="demo/2026/01/sales.csv")["Body"].read().decode())
s3_rm("demo/")

Check your understanding

Is curated/orders/ a real folder in S3?

No. S3 stores flat keys, and curated/orders/ is just a shared prefix that tools display as a folder.

Why can a reader see a half-replaced dataset, if S3 is strongly consistent?

The guarantee is per object. Replacing a dataset takes many separate requests, with no transaction across them.

What selects LocalStack over real AWS: the bucket name, or the endpoint setting?

The endpoint setting. The s3a:// path alone doesn't choose where it goes.

Lambda: short functions that react to events

You upload a handler, and AWS runs it when something happens, with no server to manage. In data pipelines, its usual job is to notice a new file and start the real work. It stops after 15 minutes at most, so a Spark job doesn't belong inside it.

Example: deploy a handler and call it
code = """
def handler(event, context):
    total = sum(event["amounts"])
    return {"total": total, "count": len(event["amounts"])}
"""
deploy_lambda("glue-lab-demo", code)

response = lam.invoke(FunctionName="glue-lab-demo", Payload=json.dumps({"amounts": [10, 20, 30]}).encode())
print(response["Payload"].read().decode())
lam.delete_function(FunctionName="glue-lab-demo")
Output from a real run

Consistency and what overwrite really means

After a PUT to S3, will the next GET return the new data? So why can a reader still see a half-replaced dataset when Spark overwrites a folder?

Show answerHide answer

S3 has strong read-after-write consistency for each object, so a successful PUT is visible to the next GET or LIST.

Q9 Glue basicsDiscussion

What is AWS Glue, really?

A colleague says "Glue stores our tables." What's wrong with that? Name the main parts of Glue and say what each one does. Which of them does a Spark job need?

Show answerHide answer

"Glue" is several separate products sharing one name:

Job bookmarks: what they do, and building your own

What do job bookmarks do, and what are their limits? Build the same idea yourself: process only the files that haven't been processed yet, and keep the state in S3. When should the state be saved?

Show answerHide answer

Bookmarks let a Glue job remember what it has read, so the next run takes only new data. They work through Glue's readers, and they rely on transformation_ctx and job.commit(). For S3 sources, they compare object modification times. So a file that changes is reprocessed in full, which duplicates rows if your output only appends, and an object carrying an older timestamp can be missed.

Your own version has the same core rule: save the state only after the output is safely written. If the job dies before that, the next run repeats the work, so the write needs to be safe to repeat.

Solution: a small file bookmark

    new = [k for k in s3_keys("q/book/landing/") if k not in done]

    df.write.mode("append").parquet(f"{S3}/q/book/out/")
    s3_put(STATE, json.dumps(sorted(done | set(new))))    # only after the write succeeds
    return n

Crawlers: useful, and how they can hurt

What does a crawler do? When would you use one instead of defining a table yourself? List what can go wrong with one on a production prefix.

Show answerHide answer

A crawler samples files under an S3 path, infers a schema and partitions, then creates or updates catalog tables. It's great for discovery and for exploring new data.

What can go wrong:

  • Wrong types: inference from a sample can pick a type that doesn't fit other files.
  • Too many tables: files with different schemas under one prefix can produce many tables, one per folder.
  • Schema changes: by default it may update a table that consumers rely on. Set the schema change policy on purpose.
  • Slow and wasteful: scanning a large bucket repeatedly just to find a known new partition.

For a stable pipeline, define the table in code, and register partitions directly from the job.

Workers, DPUs and how to size a job

What's a DPU, and how do G.1X and G.2X workers differ? How do NumberOfWorkers map to Spark executors? A job shuffles 200 GB. How would you pick a starting size, and what should you check before just adding workers?

Show answerHide answer

A DPU is Glue's unit of capacity. A G.1X worker is 1 DPU (4 vCPU, 16 GB), and a G.2X is 2 DPUs (8 vCPU, 32 GB). You pay for DPU time, so doubling workers doesn't help if the job can't use them.

Typically, one worker runs the driver, and each other worker runs one executor. So 10 G.1X workers give about 9 executors and 36 task slots.

Start from the data: 200 GB at about 200 MB per shuffle partition is about 1000 partitions. Before adding workers, check for skew, too many small files, and unnecessary data read. Workers can't fix a key that sends everything to one task. --enable-auto-scaling can reduce idle cost.

Sizing calculator
def glue_plan(shuffle_gb, workers, vcpu_per_worker=4, target_mb=200):
    executors = workers - 1
    slots = executors * vcpu_per_worker
    partitions = int(shuffle_gb * 1024 / target_mb)
    return dict(executors=executors, task_slots=slots, shuffle_partitions=partitions,
                rounds_of_tasks=round(partitions / slots, 1))

Upsert with MERGE

Apply a batch that corrects order 102 and adds order 104 using MERGE INTO. Then give the source a duplicate key and run it again. What happens, and how should a real pipeline prepare its source?

Show answerHide answer

MERGE updates matches and inserts new rows in one atomic commit. It requires at most one source row per target key, and otherwise fails, because it can't tell which one should win.

Iceberg doesn't enforce primary keys, so deduplicating the batch is your job: keep the newest event per key with row_number, using a deterministic order. Also make sure a late, older event can't overwrite newer data, for example with a timestamp condition in WHEN MATCHED.

    (102, 1002, 700.00, DATE'2026-10-26'),
    (103, 1003, 900.00, DATE'2026-11-02')""")

Q48 Iceberg internalsLab

Copy-on-write vs merge-on-read

What's the difference between copy-on-write and merge-on-read? Switch a table to merge-on-read, update a row, and find the delete file. Which does Athena use? What's the long-term cost of merge-on-read?

Show answerHide answer
  • Copy-on-write rewrites each data file holding a changed row. Writes cost more, while reads stay simple. This is Spark's default.
  • Merge-on-read writes a small delete file plus new rows, and readers combine them. Writes are cheap, but reads get slower as delete files pile up.

The guide notes Athena's row-level changes always use merge-on-read with positional deletes. So tables updated from Athena need regular compaction.

Compaction and snapshot expiry

Many small inserts leave many small files. Compact them, and check that the row count and the logical data stay the same. Do the old files disappear right away? What removes them, and what do you lose?

Show answerHide answer

rewrite_data_files combines small files into larger ones in a new snapshot. Readers aren't affected, and the rows don't change. The old files stay, because older snapshots still reference them.

Q62 Iceberg internalsLabBe careful

Concurrent writers and commit conflicts

Two jobs write to the same Iceberg table at once. Walk through what happens at commit time. When does a retry succeed, when does it fail, and how would you design around it? Why does this lab's Hadoop catalog need extra care?

Show answerHide answer

Each writer plans from the snapshot it read, writes its files, then tries to swap the catalog pointer atomically. Only one swap can win. The loser re-reads the new metadata and checks whether its change still applies:

  • Appends rarely conflict, and usually retry and succeed.
  • Updates, deletes and merges touching the same files may fail, because the data they read has changed.

Design around it by giving jobs separate partitions, running conflicting work in one queue, and tuning commit.retry.num-retries. Remember that Redshift doesn't automatically retry Iceberg commit conflicts, according to the guide.

This lab's Hadoop catalog relies on file rename, which isn't atomic on S3, so it's for single-writer practice only. That's fine here, but not for production on S3. GlueCatalog's atomic commit handles this on AWS.

Q65 Real-world pipelinesDiscussion

Thousands of small files an hour: one job per file?

An upstream system drops 5,000 small files an hour into S3. Your Lambda starts a Glue job for each. What breaks, and how would you redesign it?

Show answerHide answer

Glue has a minimum billed duration, plus startup time and concurrent-run limits, so one job per file is slow, expensive, and hits ConcurrentRunsExceededException. Each job also writes tiny output files.

Redesign around batches:

  • Have S3 events go to SQS, and start one job on a schedule or when enough work has built up.
  • Or skip events, and run on a schedule over everything new, using a watermark or a bookmark.
  • Compact the output, and use groupFiles when reading many small inputs.

Keep events per file only when files are rare and each one matters straight away. A useful question to ask is how fresh the data really has to be.

Diagnosis: a Glue job got much slower and more expensive

A daily Glue job went from 20 minutes to 3 hours after data grew a little. Doubling workers barely helped. It reads thousands of JSON files from S3, joins to a dimension and writes Parquet. What would you look at, in order?

Show answerHide answer

If more workers barely help, the bottleneck probably isn't compute capacity. Check these in the Spark UI (Glue can write its event logs to S3):

  • Driver listing: long gaps before any stage starts suggest slow listing of many small files. Group them, and compact the source.
  • One stage dominates: compare max with median task time. A big gap means skew. Look for NULL or default keys.
  • Join fan-out: compare row counts before and after the join. Growth means duplicate keys in the dimension.
  • Reading everything: check for a partition filter or push_down_predicate.
  • JSON parse costs: a schema-inferring read of many JSON files scans them all. Pass a schema, and convert to Parquet early.
  • Output files: partitionBy without a repartition can create huge numbers of small files, and S3 throttling (503 SlowDown).

Only after that, change the worker count or type.

Glue vs EMR vs Athena: which and when

You're choosing between Glue jobs, EMR and Athena for a new batch pipeline. What questions decide it? Could they be used together? What does each one cost you to operate?

Show answerHide answer

They overlap, and most lakes use several:

  • Athena: serverless SQL for ad hoc analysis and simple SQL transformations. Pay per data scanned.
  • Glue jobs: serverless Spark for typical ETL, with no cluster to run. Less control over tuning and libraries, and billed by DPU time.
  • EMR: more control over Spark versions, instance types, spot capacity and configuration, which suits large or specialized workloads. You own more of the operations.

Questions to ask: How complex is the logic? How big and how steady is the workload? Does the team need fine tuning? Who'll run it on call? What's the cost at actual volume?

A common design: Glue or EMR writes Iceberg, the Glue Catalog is shared, and Athena or Redshift serves BI.

Redshift's three kinds of table

A Redshift user says "we can UPDATE our S3 tables from Redshift now." What three table types could they mean, and what can each do? Where does the data live for each?

Show answerHide answer
  • Internal table: data in Redshift-managed storage, full INSERT, UPDATE and DELETE, no Glue needed.
  • Spectrum external table over plain Parquet: data in S3, defined in Glue. SELECT, and supported INSERT, but no UPDATE or DELETE.
  • Writable Iceberg table: data in S3, registered in Glue. DML commits through the catalog, like any other Iceberg writer.

So the claim is true only for the third, on a supported configuration. Redshift doesn't automatically retry Iceberg commit conflicts, so failed statements must be rerun.
