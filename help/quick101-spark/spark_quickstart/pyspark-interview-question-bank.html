Connect to Spark from Jupyter

Spark and JupyterLab both run on the Mac Ultra. Your own computer only shows the notebook in a browser, so there's nothing to install on it.

The environment setup is already written up, so this walkthrough doesn't repeat it. These steps point to the guides in help/quick101-spark/spark_quickstart/ in the sparksql-awsglue repo.

  1. Check that the environment exists on the Mac

    The lab lives in ~/spark-glue-local-lab. If it's missing, follow Steps 1 to 6 of setup-mac-local-spark.md, which install Java, Python 3.11, PySpark 3.5.6, pandas, pyarrow and JupyterLab. You can skip LocalStack, because these questions only use local files.

    On the Mac
    cd ~/spark-glue-local-lab
source .venv/bin/activate
python -c "import pyspark; print(pyspark.__version__)"

  2. Start JupyterLab on the Mac

    The first time, set a password (Step 20 of setup-mac-local-spark.md). Then start the server and leave that terminal open (Step 21).

    First time only
    jupyter server password
    Every session
    jupyter lab --ip=0.0.0.0 --port=8888 --no-browser

  3. Open it from your computer

    Find the Mac's address (Step 22), then open http://MAC_IP:8888/lab in your browser and sign in with that password. setup-jupyter-remote-access.md covers firewall problems and other troubleshooting. Use this only on your trusted home network, and don't set up router port forwarding.

    On the Mac
    ipconfig getifaddr en0

  4. Choose the right kernel

    The kernel decides which Python runs your code. Register the lab's environment once (Step 23), refresh the browser, then create a notebook with the Spark Lab (LocalStack) kernel. The name mentions LocalStack, but these questions don't need LocalStack running.

    On the Mac, with the environment active
    python -m ipykernel install --user --name spark-lab --display-name "Spark Lab (LocalStack)"

    A different kernel can look fine and then fail with No module named pyspark. The smoke test below prints the kernel's path so you can check.

  5. Run the smoke test

    Paste this into the first cell and press Shift+Enter. It checks the kernel, starts a Spark session, runs a DataFrame job and a SQL query, and starts a Python worker. The first run can take several seconds.

    Smoke test cell
    # ===== SMOKE TEST: paste into the first cell of a new notebook =====
import os, sys

# 1. Is this notebook using the lab environment?
print("Python:", sys.version.split()[0])
print("Kernel path:", sys.executable)

# Make Spark's Python workers use the same Python as this notebook
os.environ["PYSPARK_PYTHON"] = sys.executable
os.environ["PYSPARK_DRIVER_PYTHON"] = sys.executable

# 2. Start Spark. getOrCreate() reuses a session if this kernel already has one.
from pyspark.sql import SparkSession, functions as F

spark = (
    SparkSession.builder
    .appName("jupyter-smoke-test")
    .master("local[2]")
    .getOrCreate()
)
print("Spark:", spark.version, "| master:", spark.sparkContext.master)

# 3. Run a real job: DataFrame API and Spark SQL
df = spark.createDataFrame(
    [("books", 10), ("books", 20), ("grocery", 5)],
    "category string, amount int",
)
df.groupBy("category").agg(F.sum("amount").alias("total")).orderBy("category").show()

df.createOrReplaceTempView("smoke")
spark.sql("SELECT COUNT(*) AS row_count FROM smoke").show()

# 4. Check that Python workers run. This is the step a wrong kernel usually breaks.
double_it = F.udf(lambda x: x * 2, "int")
print("UDF on a Python worker:", df.select(double_it("amount")).first()[0])

print("SMOKE TEST PASSED")

spark.stop()   # release this session; restart the kernel before running the setup cell

    If the smoke test fails
    No module named pyspark
    Wrong kernel. Use Kernel > Change Kernel to pick Spark Lab. Repeat step 4 if it isn't listed.
    JAVA_GATEWAY_EXITED or a Java error
    Spark 3.5 needs Java 17. Check Step 2 of setup-mac-local-spark.md, and that JupyterLab was started from a terminal where java -version works.
    The DataFrame job works but the UDF line fails
    Spark's Python workers aren't using the kernel's Python. Keep the two os.environ lines at the top of the cell, then restart the kernel.
    Settings seem to be ignored
    getOrCreate() returns the session this kernel already has, and ignores new settings. Use Kernel > Restart Kernel, then run the cell again.

Q1 Spark basics

Transformations vs actions

Sort these into transformations and actions, and say which ones start a Spark job: select, filter, show, withColumn, count, groupBy().agg(), write.parquet, join, collect. Then build a chain of three transformations and prove nothing has run until you call an action.

Show answerHide answer

Transformations (select, filter, withColumn, groupBy().agg(), join) only extend a logical plan and return a new DataFrame. Actions (show, count, collect, write.parquet) make Spark optimize the plan and start a job.

This lazy evaluation is what lets Catalyst push filters down and drop unused columns before any data is read. It also explains why an error from a bad value often appears at the final write, long after the line that caused it.

        .select("order_id", "amount_x2"))

plan.orderBy("order_id").show(3)   # the action: work happens here
print("Jobs started by the action?", len(sc.statusTracker().getJobIdsForGroup("lazy_demo")) > 0)
sc.setJobGroup("", "")

Q60 Partitioning & filesBe careful

Explain these three and show the partition count and file count each produces: repartition(4), coalesce(1), write.partitionBy('category'). Why can coalesce(1) hurt so much?

Show answerHide answer

Show answerHide answer

Parquet has no UPDATE, so you build the new full state: unchanged rows (left_anti) + all incoming rows.

mode("overwrite") deletes the target path, and reads are lazy. With a plain filter, the input files are deleted before tasks read them, so the job fails and the table is gone. With a join and AQE on, it may succeed, because AQE has already run the shuffle stages and saved their output before the delete. That's an accident of the plan, not a guarantee. Turn AQE off, remove the shuffle, or lose an executor at the wrong moment, and the table is destroyed. The DataFrame is also unusable afterwards, because it still points at deleted files.

Write to a new versioned location, validate, then switch readers over with a catalog update or pointer. cache() isn't a safe workaround either: if a cached block is lost, Spark recomputes it from the deleted files.

High-watermark incremental load

Load only rows newer than the last processed updated_at. Handle the first run with no watermark, late-arriving rows, and an empty batch. Where do you save the watermark, and when?

Show answerHide answer

Read the watermark, pull rows after it with a lookback window for late arrivals, dedupe by key, write, and only after a successful write save the new watermark. If you save it first and the job fails, that data is skipped forever.

max() of an empty batch is NULL, so don't advance the watermark in that case. The lookback means rows get processed twice, so the target write must be idempotent, such as a key-based merge or a partition overwrite.

Solution
src = raw_orders.withColumn("updated_at", F.to_timestamp("updated_at"))

def run_batch(watermark, lookback_hours=24):
    batch = src
    if watermark is not None:
        batch = src.filter(F.col("updated_at") > F.expr(
            f"CAST('{watermark}' AS TIMESTAMP) - INTERVAL {lookback_hours} HOURS"))
    w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc(), F.col("event_id").desc())
    batch = batch.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn").cache()
    new_max = batch.agg(F.max("updated_at").cast("string")).first()[0]   # keep it as text in the session time zone
    n = batch.count()
    batch.unpersist()
    return n, (new_max or watermark)

print("first run rows:", n1, "| watermark:", wm)
n2, wm2 = run_batch(wm)
print("next run rows :", n2, "(reprocessed by the lookback) | watermark:", wm2)

A broadcast sends the small table to every executor, so no shuffle is needed. It's excellent for small dimensions. spark.sql.autoBroadcastJoinThreshold (10 MB by default) controls it automatically, and the broadcast() hint overrides it.

            return s

Q81 Performance

Stack overflow from long lineage

A loop runs df = df.transform(...) hundreds of times and eventually fails with StackOverflowError or just gets extremely slow before any task runs. What's going on? Show how to measure it and how to fix it.

Show answerHide answer

Transformations build a plan rather than running anything, so every iteration makes the plan deeper. Catalyst walks that tree recursively, so the driver spends its time analyzing, then eventually overflows its stack. This isn't an executor memory problem. Adding executor memory won't help.

Fixes: collapse the work into a single expression if possible, or truncate lineage every N iterations with localCheckpoint() or checkpoint(). cache() alone doesn't fix it, since it doesn't drop the logical lineage. Raising -Xss only delays the failure.

    return df._jdf.queryExecution().logical().toString().count("\n")

df = spark.range(5).withColumn("v", F.lit(0))
for i in range(50):
    df = df.withColumn("v", F.col("v") + 1)
    if (i + 1) % 10 == 0:
        df = df.localCheckpoint()
print("plan lines with a reset every 10:", depth(df))

Troubleshoot TASK_WRITE_FAILED

A write fails with Job aborted due to stage failure: Task 107 failed 4 times ... [TASK_WRITE_FAILED] Task failed while writing rows to s3://.... What does this error tell you? Walk through finding the real cause.

Show answerHide answer

Almost nothing by itself. TASK_WRITE_FAILED wraps whatever went wrong while the task ran, and that includes every lazy transformation upstream, since the write is the action that finally runs them. So don't assume S3 is at fault. Scroll to the last Caused by: in the driver log or the failed task's stderr.

Common root causes:

  • A data error, such as a UDF exception, ANSI cast failure or decimal overflow. It fails on the same partition each time. Task 107 on all 4 attempts is a strong clue.
  • Executor OOM or a killed container. Look for ExecutorLostFailure or exit code 137, usually on a skewed task.
  • S3 503 SlowDown throttling from too many files or too many partitions under a prefix, or a 403 for permissions/KMS.
  • A local disk filling up on the node.

To isolate it, run the transformations with .collect() on a small subset or write to a local path, to separate compute from storage. Then look at the data in partition 107.

In PySpark, an exception inside a Python UDF often surfaces directly as PythonException, as this demo shows, and failures on the JVM side are the ones you'll usually see wrapped in TASK_WRITE_FAILED. Either way, the write is only where the failure became visible.

  • S3 throttling or connection pool limits, particularly with many small files.
  • Files deleted during the job: the listing happened earlier, but an overwrite removed them before the read (FileNotFoundException).

If there are filters or transformations ahead of the count, none of this applies, because count has to compute them first.

Driver OOM vs executor OOM

How do you tell driver OOM from executor OOM? What causes each? Explain unified memory, and what spark.executor.memoryOverhead is for. How would you size executors for a cluster of 16-core, 64 GB nodes?

Show answerHide answer

Driver OOM: collect, toPandas, big broadcasts, a huge plan or many millions of files listed. The whole application dies.

Executor OOM: skewed partitions, a large collect_list, a wide row, or too many cores sharing the same heap. YARN "killed by exceeding memory limits" or exit code 137 means off-heap usage went past the container's limit, and that's usually fixed by more overhead rather than more heap.

Heap layout: spark.memory.fraction (0.6) is unified memory for execution and storage, which borrow from each other. The rest is user memory for your data structures and metadata. Overhead covers JVM native memory and network buffers, and Python workers, if spark.executor.pyspark.memory isn't set. PySpark jobs often need more of it.

Sizing: a usual starting point is about 5 cores per executor. On a 16-core, 64 GB node, leave a core and some memory for the OS and daemons, which gives 3 executors with 5 cores each. Memory is about 63 / 3 = 21 GB, minus around 10% overhead, so about 18 to 19 GB of heap. Then adjust according to what you observe.

Size spark.sql.shuffle.partitions

Show answerHide answer

Aim for about 100 to 200 MB per shuffle partition: 500 GB / 200 MB is about 2500 partitions.

Too low: partitions are huge, so you see spill, slow tasks and OOM. Too high: lots of tiny tasks, so scheduling overhead rises, and without AQE you also get many small output files.

Make a pipeline idempotent

Show answerHide answer

Idempotent means that running the job again for the same input gives the same output, with no duplicates and no gaps.

Tie each run to a logical date passed in as a parameter (not current_date()), and write with dynamic overwrite of that date's partition, so a rerun replaces that day's data. append isn't idempotent, since a retry after a partial failure doubles the data.

Also remember a failed write can leave partial files. Readers need a way to avoid half-written output: _SUCCESS, a catalog partition added only after validation, or a table format with atomic commits.

           .withColumn("dt", F.lit(run_date))
           .write.mode("overwrite").option("partitionOverwriteMode", "dynamic")
           .partitionBy("dt").parquet(out))

load("2026-01-05")       # rerun

Plain Parquet vs Iceberg/Delta, with MERGE

What specific problems do Iceberg and Delta solve that a folder of Parquet can't? Write the MERGE INTO you'd use for an upsert. What maintenance do they need? (This code is for reference only: it needs an Iceberg or Delta catalog, which this lab's session doesn't have.)

Show answerHide answer

A table format adds a metadata layer that records exactly which files make up each version of a table. That gives you:

  • Atomic commits: readers see the old or new snapshot, never half of a write.
  • MERGE, UPDATE and DELETE, plus concurrent writer conflict detection.
  • Time travel and rollback.
  • Schema and partition evolution without rewriting data.
  • Skipping file listings, which can be very slow on S3.

Maintenance doesn't go away, though: compact small files, expire old snapshots, remove orphan files. A format also doesn't deduplicate your MERGE source. If the source has duplicate keys, MERGE fails or does the wrong thing, so dedupe it first.

A catalog is not the data: Glue stores metadata and locations. Dropping an external table leaves its files, and deleting the files leaves a table pointing at nothing.

Merge overlapping time intervals

Each row is a (user, start_ts, end_ts) booking. Merge overlapping or touching intervals per user, and compute the total covered minutes without double counting.

Show answerHide answer

Sort by start. Track the maximum end time of all previous rows with a window. A row starts a new group when its start is later than that maximum. A running sum of the flag gives each group an ID, then take min start and max end.

Comparing only with the previous row's end (lag) is a common bug. A long interval can contain several short ones, so you need the running maximum.

Solution
b = spark.createDataFrame([
    ("a", "09:00", "10:00"), ("a", "09:30", "12:00"), ("a", "09:45", "10:15"),
    ("a", "11:30", "13:00"), ("a", "14:00", "15:00"), ("b", "08:00", "08:30"), ("b", "08:30", "09:00"),
], "user_id string, s string, e string").select(
    "user_id",
    F.to_timestamp(F.concat(F.lit("2026-03-01 "), "s")).alias("start_ts"),
    F.to_timestamp(F.concat(F.lit("2026-03-01 "), "e")).alias("end_ts"))

w = Window.partitionBy("user_id").orderBy("start_ts", "end_ts")
prior = w.rowsBetween(Window.unboundedPreceding, -1)
merged = (b.withColumn("max_prev_end", F.max("end_ts").over(prior))
           .withColumn("new_group", F.when(F.col("max_prev_end").isNull() | (F.col("start_ts") > F.col("max_prev_end")), 1).otherwise(0))
           .withColumn("grp", F.sum("new_group").over(w.rowsBetween(Window.unboundedPreceding, 0)))
           .groupBy("user_id", "grp").agg(F.min("start_ts").alias("start_ts"), F.max("end_ts").alias("end_ts")))

(merged.withColumn("mins", (F.col("end_ts").cast("long") - F.col("start_ts").cast("long")) / 60)
       .orderBy("user_id", "start_ts").show())
